# 执行修复

**核心目标**: 严格按用户已确认的修复方案 (「方案设计」产出) 执行 issue 修复。
**用户负责决策, AI 只负责执行; 过程中关键决策用 question 提问, 所有执行先取得用户授权.**

## 执行原则

- **按方案执行**: 只改方案确认过的文件/范围; 若执行中发现新问题或偏离方案 → 停下来用 question 问用户
- **决策权在用户**: 任何关键决策 (改哪里 / 怎么改 / 要不要改方案) 必须 question 用户, 不得擅自决定
- **写操作需授权**: 改代码 / 增删文件 / 跑破坏性命令, 先经用户确认 (permission 审批)
- **小步提交**: 每完成一个逻辑单元, 向用户简报

## 前置检查

1. 确认已有用户确认过的方案文档 (`docs/numas/<issue>-fix-plan.md` 或用户指定位置)
2. 没有方案 → 提醒用户先完成「方案设计」, 不要直接开改

## 执行流程

### 1. 复述方案 + 确认执行范围

- 简要复述方案: 改动文件清单 / 实现思路 / 验收标准
- 用 question 确认: **开始执行?** (列出改动文件范围)

### 2. 逐项执行修复 (关键处 question)

- 按方案顺序逐项修改:
  1. 定位到目标文件
  2. 说明"这里要改成什么" → 改代码
  3. **实现遇到多种做法 / 影响边界 / 取舍** → question 用户再定
  4. 改完一项, 简报该项结果
- 每一步改动:
  - 不夹带方案外的无关改动
  - 不夹带调试代码/临时文件
  - commit message 用 conventional commit 风格 (小步提交, 每单元可独立回滚)

### 3. 运行验证

- 按方案里的测试方式验证:
  - 跑项目既有测试 / 格式化 / lint
  - 复现 issue 场景, 确认现象消失/达成期望行为
- 验证失败 → 分析原因, 用 question 与用户确认下一步 (调整实现 / 改方案 / 环境问题)

### 4. 汇报 + 用户验收确认

- 向用户报告: 改动摘要 / 测试结果 / 本地验证方式
- **等用户确认验收通过** (用 question: 验收通过? / 需要调整)
- 未通过 → 回到步骤 2 或经 question 回「方案设计」修正方案

### 5. 收尾

- 确认方案文档 (fix-plan) 是否随代码一起保留/提交 (用户决定)
- 告知用户可进入「提交PR」步骤

## 注意事项

- **不替用户决策**: 即使感觉"明显该这么改", 关键决策也要 question
- 执行中发现方案有缺陷 → 停下, 用 question 让用户决定 (改方案 / 继续 / 回滚)
- 所有 shell 写操作 (改文件 / 建目录 / 跑测试) 经授权后执行
- 遵循项目根 AGENTS.md 的日志规则, 关键交互落盘到 `.logs/{YYYYMMdd}.log`
