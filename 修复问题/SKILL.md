# 修复问题

围绕任务 issue, 与用户协作完成「理解问题 → 设计方案 → 执行修复 → 验收 → 保留产物」全流程.
**所有方案必须由用户确认后才执行** (AI 不擅自决定).

## 执行流程

### 1. 理解 issue

- 执行 `gh issue view <issue 编号> --repo <原仓库> --json title,body,labels,comments` 读取结构化内容
- 向用户复述: 问题背景 / 期望功能 / 验收标准 (提炼 issue 里的关键条目)
- 与用户确认理解一致后再继续

### 2. 探索项目

- 阅读项目结构 (README / 构建脚本 / 相关目录)
- 定位与 issue 相关的代码模块、依赖、运行环境要求
- 检查本地开发环境是否满足 (语言版本 / 依赖 / 构建工具), 缺失则引导安装
- 向用户简报: 关键文件、改动范围、风险点

### 3. 设计方案 (必须用户确认)

- 提出技术方案 (2-3 个候选, 含取舍), 推荐一个
- **等用户明确选择后才进入执行**
- 方案要点: 改动文件清单 / 实现思路 / 测试方式 / 与验收标准的映射

### 4. 执行修复

- 按用户确认的方案改代码 (写操作走 permission 审批)
- 小步提交, commit message 用 conventional commit 风格
- 完成后运行项目既有检查 (测试 / 格式化 / lint)

### 5. 验收

- 向用户报告: 改动摘要 / 测试结果 / 本地验证方式
- **等用户确认验收通过**
- 未通过 → 回到「设计方案」或「执行修复」阶段修正

### 6. 保留产物

- 把修复方案写入项目文档 (建议 `<项目>/docs/numas/<issue 编号>-fix-plan.md`, 或用户指定位置)
- 内容: 问题理解 / 方案对比 / 最终方案 / 改动清单 / 验证方式 / 遗留问题
- 该文档随后续 commit 一起提交

## 注意事项

- **AI 不擅自决定方案**, 必须由用户确认
- 每步完成向用户简报, 不要长时间静默
- 环境/依赖问题优先解决 (必要时引导安装)
