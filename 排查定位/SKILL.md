# 排查定位

**核心目标**: 让用户真正理解任务 — 向用户解释 issue 的**问题现状 / 成因**, 引导用户**自己分析**,
辅助用户形成清晰的排查思路并**定位到相关代码文件**。
**AI 只做解释与引导, 不直接替用户修复问题.**

## 执行原则

- **AI 是讲解员/引导者, 不是执行者**: 本步骤不修改任何代码, 不做任何修复
- 目标是**用户理解并定位**, 让用户能清楚说出"问题是什么 / 为什么 / 大概改哪些文件"
- 每解释一层, 都与用户确认是否理解 (可结合 question 确认), 不连续倒大量信息

## 执行流程

### 1. 读取并复述 issue

- 执行 `gh issue view <issue 编号> --repo <原仓库> --json title,body,labels,comments` 读取结构化内容
- 向用户**逐条解释**: 问题背景 / 期望行为 / 当前行为 / 验收标准 (提炼 issue 关键条目)
- 用**通俗语言**转述技术内容, 避免直接丢原文
- 与用户确认: "以上是 issue 要解决的问题, 还有不理解的地方吗?"

### 2. 分析问题成因

- 结合 issue 内容与项目背景, **解释可能成因** (为什么会出现这个问题):
  - 涉及哪个功能/模块
  - 触发条件是什么 (什么输入/操作会导致)
  - 成因类型: 逻辑错误 / 边界未处理 / 版本兼容 / 依赖问题 / 文档缺失 等
- **引导用户思考**: 提问式引导, 如 "你觉得是哪种可能?" / "如果是你, 会先查哪里?"
- 不直接下结论, 让用户参与分析

### 3. 引导排查思路

- 与用户一起**设计排查路径**:
  1. 先在本地项目复现 issue (如何复现 / 跑什么命令 / 看什么现象)
  2. 从入口追到相关模块 (UI? API? 数据处理?)
  3. 缩小范围: 二分/打印/断点 等思路
- 可以用 shell **只读命令辅助定位** (grep 关键词 / 读文件 / 跑构建定位), 但**不改代码**
- 向用户展示: 关键文件路径 / 相关函数 / 依赖关系 (列表形式)

### 4. 定位问题文件

- 协助用户**定位到具体文件** (可能多个): 文件路径 + 大致行号 + 该文件在链路中的作用
- 向用户简报: "问题很可能出在这些文件" + 每个文件的嫌疑点
- **确认用户认可定位结果** 后再结束 (问用户: 定位结果 OK 吗?)

### 5. 输出排查小结

向用户汇总:
- 问题是什么 (一句话)
- 成因是什么
- 排查路径 / 定位到的文件清单
- 下一步: 告知用户进入「方案设计」步骤设计修复方案

## 注意事项

- **本步骤不做任何修复**, 修复在「执行修复」步骤
- 用户不理解时耐心解释, 用类比/举例
- 若用户想跳过分析直接让 AI 修复 → 温和提醒: 按协作规则, 方案需用户确认, 可先快速带过定位再进「方案设计」
