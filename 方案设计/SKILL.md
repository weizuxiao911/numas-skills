# 方案设计

**核心目标**: 在用户已经理解任务 (经过「排查定位」) 的前提下, **协助用户完成修复方案设计**,
形成一份**用户认可**的方案设计文档。
**AI 只负责代笔撰写方案文档, 不直接替用户做技术决策.**

## 执行原则

- **方案必须由用户拍板**: AI 提供候选/取舍分析, 但**最终选择由用户用 question 工具确认**
- **AI 是代笔者**: 方案内容以用户意志为准, AI 负责把用户的想法整理成结构化的方案文档
- 本步骤**不修改项目代码** (只写方案文档, 且文档位置/是否入库由用户定)

## 前置检查

1. 确认已完成「排查定位」— 用户理解 issue + 已定位问题文件 (可简要复述确认)
2. 若用户还没理解任务, 先回到「排查定位」, 不要跳过直接设计

## 执行流程

### 1. 复述已确认的问题与定位

- 简要复述: issue 问题 / 成因 / 定位到的文件清单
- 与用户确认: "基于以上理解, 我们开始设计修复方案?"

### 2. 探索方案空间 (AI 提供候选, 不拍板)

- 基于定位到的文件, 探索可行修复方向, 列出 **2-3 个候选方案**, 每个含:
  - 实现思路 (改哪里 / 怎么改)
  - 取舍 (改动范围 / 风险 / 侵入性)
  - 推荐哪个 + 为什么
- **用 question 工具让用户选择** (推荐项标 "(推荐)")
- 用户也可以提出自己的想法, AI 帮忙完善

### 3. 细化方案 (question 逐项确认)

- 用户选定方向后, **逐项用 question 确认关键决策点**:
  - 改动文件清单 (是否只动定位文件? 是否新增文件?)
  - 实现方式 (在哪个函数改? 新增工具函数? 复用现有?)
  - 测试方式 (怎么验证? 跑现有测试 / 手动复现)
  - 边界情况 (空输入 / 异常 / 兼容性 如何处理)
- **不连续追问过多问题**, 一次 1-2 个, 等用户答复
- 关键取舍 (如"牺牲 X 换 Y") 必须用户拍板

### 4. 代笔撰写方案设计文档

- 把确认过的方案整理成**方案设计文档**, 建议路径 `<项目>/docs/numas/<issue 编号>-fix-plan.md`
  (位置由用户确认, 或用 question 让用户选)
- 文档内容:
  - 问题理解 (issue 背景 / 成因 / 定位文件)
  - 候选方案对比 (列出 + 为什么选最终方案)
  - 最终方案 (改动文件清单 / 实现思路 / 边界处理 / 测试方式)
  - 验收标准 (如何判断修复成功 — 映射到 issue 的验收要求)
- **只写文档, 不改功能代码**

### 5. 方案确认 (最终 question)

- 把方案文档交给用户审阅, 用 question 确认: **方案 OK, 进入「执行修复」** / 需要修改
- 未确认前**不得进入执行修复**

## 注意事项

- AI 可以提建议, 但**方案最终选择权在用户**
- 若用户表示"你看着办" → 仍要用 question 给选项让用户选 (不替用户决定)
- 方案文档是否需要随代码一起提交, 由用户决定 (在「执行修复」/「提交PR」时确认)
